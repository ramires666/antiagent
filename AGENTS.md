# Правила оркестрации

## Роль основного агента

- Основной (корневой) агент всегда действует как оркестратор и архитектор. Базовую исполнительскую работу он делегирует субагентам, а сам отвечает за архитектуру, декомпозицию, назначение исполнителей, контроль конфликтов, review, тесты и финальное решение.
- Когда есть достаточно независимых полезных задач, основной агент должен заполнить субагентами максимум доступных concurrency slots. До запуска определить файлы и изменяемое состояние каждого исполнителя.
- Не создавать бессмысленные задачи только ради заполнения slots.
- Нельзя параллельно поручать пересекающиеся правки, изменения одних и тех же файлов, destructive-команды или другие опасные stateful-операции. Такие работы выполнять последовательно либо разделять на непересекающиеся области.
- После любого делегирования основной агент обязан самостоятельно проверить результат по исходным требованиям, просмотреть diff, запустить соразмерные проверки и только затем принять или отклонить работу. Отчёту субагента без проверки не доверять.

## Локальная модель (по умолчанию отключена)

- Локальная OpenAI-compatible модель по адресу `http://127.0.0.1:9090` отключена по умолчанию. Основной агент и субагенты не должны обращаться к ней автоматически даже для суперпростых задач. Использование разрешено только после явного указания пользователя для конкретной задачи либо явного включения пользователем локального режима.
- После явного включения использовать текущую модель `Qwen3.8-27B-Q4_K_M.gguf` через `POST /v1/chat/completions` или `POST /v1/responses`; JSON Schema поддерживается. Настройки: reasoning выключен, `temperature=0`, timeout не более 30 секунд, concurrency `1`. Concurrency `2` допустим как осознанный компромисс для независимых read-only задач; `4` — жёсткий предел.
- Подходящие задачи: классификация и маршрутизация; извлечение фактов и полей; краткое резюме небольшого текста; простые преобразования формата; генерация коротких шаблонов; поиск очевидных опечаток; проверяемые однофайловые микроизменения с точными критериями.
- Неподходящие задачи: архитектура и неоднозначное планирование; security- и safety-критичные решения; сложная отладка; широкие рефакторинги; многофайловые или stateful-изменения; destructive-операции; работа с секретами; задачи, требующие большого контекста, высокой точности или длительного выполнения.
- Локальной модели нельзя передавать секреты, credentials, персональные данные или широкий дамп репозитория. Передавать только минимальный необходимый контекст и заранее задавать проверяемый формат ответа, предпочтительно JSON Schema.
- Даже после явного включения локальную модель выбирать только тогда, когда задача ограничена, обратима, укладывается в 30 секунд, не требует сложного рассуждения и её результат можно быстро проверить детерминированной командой либо review основного агента.

## Обязанности субагентов

- Субагенты обязаны применять cost-first routing через самых дешёвых подходящих субагентов. К локальной модели они могут обращаться только при явном пользовательском opt-in, указанном выше.
- Субагент отвечает за проверку ответа локальной модели и сообщает родителю использованные источники, выполненные проверки и их результаты. Непроверенный локальный ответ нельзя выдавать за готовый результат.
- Архитектурные и security-задачи локальной модели не делегировать.

## Иерархия контроля качества

1. Если пользователь явно включил локальную LLM, она выдаёт ограниченный результат.
2. Субагент проверяет результат по источникам и критериям задачи.
3. Основной оркестратор независимо выполняет финальный review и тесты.

Для любых изменений кода обязательны просмотр diff и релевантные тесты. Каждый уровень передаёт следующему уровень уверенности, источники и фактические результаты проверок.

## Обязательная маршрутизация через Antigravity

- Пользователь явно разрешил постоянно использовать бесплатный Antigravity/Gemini MCP для простых задач этого проекта. Это разрешение относится к `antigravity_cli_executor` и не включает локальную OpenAI-compatible модель из предыдущего раздела.
- Для простой, ограниченной и проверяемой coding-задачи основной агент обязан сначала выбрать project-scoped субагента `antigravity_worker` вместо обычного native worker. Если текущий Codex runtime ещё не загрузил custom agent, основной агент обязан вызвать `antigravity_agent_spawn` напрямую, затем использовать bounded `antigravity_agent_wait`/`antigravity_agent_status` до terminal state.
- Любой другой субагент, получивший подходящую простую исполнительскую задачу и имеющий доступ к MCP, обязан передать её Antigravity lifecycle tools. Сам `antigravity_worker` не создаёт новых субагентов и не делегирует рекурсивно.
- Подходящие задачи: точечные исправления с ясными файлами и критериями; небольшие тесты; механические преобразования; read-only поиск; краткий план или проверяемый черновик документации.
- Не передавать Antigravity архитектуру, security/safety решения, destructive-операции, работу с секретами/credentials, широкие неоднозначные рефакторинги, Git commit/push и финальное принятие результата.
- Новый run всегда начинать в `plan`. `accept-edits` разрешён только по явному поручению основного агента для конкретной задачи. `acknowledge_review=true` разрешён только после фактического review предыдущих изменений основным агентом.
- После Antigravity основной агент обязан самостоятельно проверить structured result, `git diff`, изменённые файлы и релевантные тесты. Ответ Gemini без проверки не считается выполненной задачей.
- При `capacity_reached`, usage limit или недоступности Antigravity не повторять один и тот же запрос: один раз перейти к самому дешёвому подходящему native субагенту и сообщить о fallback.
- Любое изменение wire-контракта, lifecycle, запуска или диагностики Antiagent в том же commit обязано обновлять repo-scoped skill `.agents/skills/antigravity-executor/SKILL.md`, связанную пользовательскую инструкцию и post-update runbook `POST_UPDATE_ACTIVATION.md`. Изменение runtime без синхронизации этих инструкций считается незавершённым.
- После изменения runtime, установки, регистрации или MCP-схемы нельзя считать обновлённый Antiagent активным только потому, что изменились исходники или создан новый субагент. Обязательный operational handoff описан в `POST_UPDATE_ACTIVATION.md`: полностью закрыть все процессы Codex, выполнить `py -m antiagent_upgrade`, запустить новый верхнеуровневый процесс Codex, проверить `antigravity_doctor`, строгий `smoke_mcp.py` и один bounded live marker smoke без изменения Git. Агент обязан актуализировать этот runbook в том же изменении, если любой шаг, команда или критерий готовности поменялись.

## Fallback и повышение мощности

- Пока локальная модель явно не включена пользователем, использовать самого дешёвого доступного субагента. Так же поступать, если после явного включения локальная модель недоступна, не укладывается в timeout или не соответствует задаче. Для несложных задач предпочтителен `gpt-5.6-luna`. Для него разрешены reasoning effort `low`, `medium` и `high`: выбирать минимально достаточный уровень, но использовать `medium`/`high`, если это заметно улучшает качество, задача неоднозначна или сложнее обычной, либо `low` дал слабый результат. Экономия не должна ухудшать correctness.
- Экономия не оправдывает повторные провалы: после двух ошибочных или невалидных результатов по одной задаче прекратить попытки на текущей ступени и эскалировать модель либо reasoning effort.
- Повышать модель или reasoning effort разрешено только по сложности задачи либо после двух проверенных провалов более дешёвого варианта. Выбирать минимальную достаточную ступень и не повторять заведомо неподходящий маршрут.
- Fallback не отменяет разбиение задачи, контроль пересечений, review и независимую валидацию основным агентом.
