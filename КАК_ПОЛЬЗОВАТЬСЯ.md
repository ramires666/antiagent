# Как начать пользоваться Antigravity в Codex

На этом компьютере всё уже установлено и подключено. Вам не нужны API-ключи.

## Первый запуск

1. Полностью закройте Codex и откройте его снова. В Codex CLI нажмите `Ctrl+C`, а затем запустите его заново. Это нужно сделать один раз, чтобы Codex увидел новый инструмент.

2. Откройте самую верхнюю папку проекта, с которым хотите работать. Это должен быть корень Git-репозитория — обычно в нём находится скрытая папка `.git`.

3. Если запускаете Codex из PowerShell, сначала перейдите в папку проекта.
   Вместо `<КОРЕНЬ_GIT_ПРОЕКТА>` подставьте фактический путь текущего проекта:

   ```powershell
   Set-Location "<КОРЕНЬ_GIT_ПРОЕКТА>"
   codex.cmd
   ```

4. Для обычной простой задачи дайте Codex такой запрос:

   ```text
   Передай эту задачу project-agent antigravity_worker.
   Пусть он выполнит её через Antigravity сначала в mode=plan.
   После terminal result самостоятельно проверь результат, git diff и тесты.
   ```

5. Если план устраивает и нужны изменения файлов, напишите:

   ```text
   Разрешаю antigravity_worker выполнить именно этот план в mode=accept-edits.
   acknowledge_review=false.
   После terminal result сам проверь git diff и запусти подходящие тесты.
   ```

В предыдущем запросе вы попросили Codex проверить `git diff` и тесты. Всё равно просмотрите итоговый список изменений перед коммитом.

`working_directory` может быть абсолютным или относительным к каталогу, из которого запущен MCP process, и должен указывать точно на корень Git-репозитория. После раскрытия `..` и ссылок путь обязан совпадать с каталогом process или находиться внутри него; выход наружу отклоняется. Пустое значение по умолчанию использует текущий Git-root Codex и является рекомендуемым для обычного вызова.

## Что делает `antigravity_worker`

`antigravity_worker` — нативный project-scoped субагент Codex с read-only sandbox. Он сам не пишет файлы и не запускает shell: он управляет только MCP lifecycle Antigravity:

1. `antigravity_agent_spawn` сразу создаёт durable run и возвращает `agent_id`;
2. `antigravity_agent_wait`/`antigravity_agent_status` получают состояние и результат;
3. `antigravity_agent_followup` продолжает terminal conversation через `agy --conversation`;
4. `antigravity_agent_interrupt` отменяет run и дерево CLI-процессов;
5. `antigravity_agent_list` показывает до 100 последних runs текущего Git workspace.

Terminal history хранится в приватной пользовательской SQLite БД: `%LOCALAPPDATA%\antiagent\agents.sqlite3` на Windows. Исходные `task`, `context` и `verification` в БД не записываются. Хранятся IDs, workspace, состояния, timestamps, conversation ID и ограниченный итоговый structured result. История ограничена 1000 terminal runs, одновременно разрешено не более 32 active runs, один сохранённый result — не более 256 KiB.

Если MCP process аварийно завершился, уже запущенный OS-процесс нельзя присоединить к новому process. Зависший run позже получает `failed/manager_lost`; для немедленного продолжения процессов после crash понадобился бы отдельный daemon, которого в минимальной версии нет.

## Готовое правило для Codex

В этом проекте правило уже находится в `AGENTS.md`. Для другого проекта можно передать Codex или добавить в его `AGENTS.md` этот блок:

```text
Для каждой простой, ограниченной и проверяемой coding-задачи сначала используй
project-agent antigravity_worker вместо обычного native worker. Если custom agent
ещё не загружен, вызови antigravity_agent_spawn напрямую и жди terminal state
через bounded antigravity_agent_wait/status. Всегда начинай с mode=plan.
accept-edits разрешён только после моего явного решения; acknowledge_review=true —
только после фактической проверки предыдущего diff. Не передавай Antigravity
архитектуру, security, destructive-операции, секреты, commit или push. После его
ответа основной Codex обязан сам проверить structured result, git diff и тесты.
При usage limit/capacity/unavailable не повторяй запрос: один раз переключись на
самого дешёвого подходящего native субагента.
```

Это правило максимально приближает Antigravity к замене исполнителей Codex, но не подменяет native UI/thread, forked context, sandbox approvals и lifecycle самого Codex. Эти функции остаются у Codex; Gemini выполняет leaf coding work.

## Ручной вызов без custom agent

Если `antigravity_worker` ещё не появился в текущей сессии, полностью перезапустите Codex. До перезапуска можно вызвать старый совместимый tool напрямую:

```text
Используй antigravity_cli_execute.
Сначала изучи проект и составь план. Ничего не изменяй.
thinking_level: low
mode: plan
working_directory:
acknowledge_review: false
```

Режим по умолчанию — `plan`. Для записи всегда явно указывайте `mode: accept-edits`; при первом безопасном editing-вызове `acknowledge_review` оставьте `false`. Если предыдущий вызов оставил частичный или неизвестный diff, wrapper вернёт `error_type: review_required`: сначала вручную проверьте diff и только затем повторите вызов с `acknowledge_review: true`. Автоматического rollback нет.

Каждый ответ содержит `run_id`, временные метки, `duration_seconds`, `exit_code`, `error_type`, `retryable`, фактическую `cli_version` (если её удалось получить), признаки `metadata_complete`, `usage_available`, `conversation_id_available`, а также Git postflight: `preexisting_dirty`, `worktree_changed`, `changed_paths`, `postflight_complete`, `requires_review`. Wrapper timeout — 840 секунд; project-scoped Codex timeout — 900 секунд.

## Какой thinking выбрать

- `low` — простая и быстрая задача: посмотреть файлы, найти место, сделать небольшой план.
- `medium` — обычная работа с кодом. Используйте этот вариант по умолчанию.
- `high` — сложная ошибка или задача, где нужно особенно внимательно подумать. Работает дольше.

`thinking_level` — это глубина обдумывания, а не уровень доступа к компьютеру.

## Если открылся браузер Google

Это вход в Antigravity через ваш аккаунт. Войдите и разрешите доступ. Пароль, cookies и токены нельзя вставлять в сообщения Codex или сохранять в проекте.

Обычно вход нужен только один раз. Если позже появится ошибка входа, откройте PowerShell, запустите `agy` и завершите вход в браузере.

## Если Codex не видит инструмент

В PowerShell выполните:

```powershell
codex.cmd mcp get antigravity_cli_executor
```

Если команда без ошибки показала настройки сервера, полностью перезапустите Codex. Надпись `Auth: Unsupported` для этого локального инструмента нормальна: вход выполняет программа `agy`, а не сам MCP.

Если написано `No MCP server named`, сначала из Git-root Antiagent установите
переносимую команду, затем зарегистрируйте её и снова перезапустите Codex:

```powershell
py -m pip install --user pipx
py -m pipx ensurepath
py -m pipx install .
codex.cmd mcp add antigravity_cli_executor --env ANTIAGENT_EXECUTION_BOUNDARY=host -- antiagent-mcp
```

## Как проверить MCP

Из Git-root Antiagent выполните:

```powershell
.venv\Scripts\python.exe -m unittest discover -v
```

Автоматические тесты не расходуют OAuth- или веб-лимиты и не запускают настоящий `agy`: они используют безопасные заглушки и локальные тестовые процессы.

Во время обычного вызова MCP отправляет события progress: запрос поставлен в очередь (`queued`), началось выполнение (`running`), а при долгой работе примерно каждые 12 секунд приходит heartbeat. Конкретный MCP-клиент может не показывать эти события. Независимо от их отображения итоговый результат и ошибки остаются structured-ответами MCP.

## Что было удалено ради безопасности

Из запуска удалён флаг `--dangerously-skip-permissions`. Его название буквально означает «опасно пропустить проверки разрешений».

С этим флагом агент мог бы без подтверждения запускать команды и обращаться к доступным компьютеру файлам. Ошибка модели, вредная инструкция внутри чужого репозитория или prompt injection могли бы привести не только к неправильной правке проекта, но и к чтению других файлов, запуску процессов или утечке данных.

Режим `accept-edits` **не удалён**: агент по-прежнему может менять файлы проекта. Сохранены проверки разрешений, обязательный sandbox, работа только из корня Git-репозитория и последующая проверка изменений основным Codex.

### Почему вам не предложили просто включать опасный режим

Опасный переключатель нельзя безопасно передавать самой модели как обычный параметр: тогда модель могла бы включить его без отдельного решения человека. Кроме того, MCP работает без интерактивного окна подтверждения, а sandbox в Windows является дополнительной защитой, но не абсолютной стеной.

Поэтому я выбрал безопасное поведение по умолчанию. Но я должен был сразу отдельно сообщить вам об этом решении — это была моя ошибка в коммуникации.

Право выбора остаётся за вами. Если такой режим действительно понадобится, его следует делать отдельной ручной настройкой вне параметров MCP и использовать только в изолированной виртуальной машине или контейнере без секретов. Сейчас опасный режим выключен.
